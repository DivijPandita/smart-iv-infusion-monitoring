# Smart IV Infusion Monitor: Dual-Sensor EKF Fusion

> **This is a software simulation/prototype. It is not a certified medical device and must not
> be used for patient care.** All sensor data are generated by Python.

Predictive IV infusion monitoring using two *simulated* sensors, a load cell and an IR drop
counter, fused by an Extended Kalman Filter (EKF) to estimate flow rate and the tubing's
actual drop factor, predict remaining infusion time with a confidence interval, and raise
predictive alerts on an interactive dashboard.

```text
Simulated sensors -> preprocessing -> EKF fusion -> flow + drop factor
                  -> remaining volume/time -> confidence interval -> alerts -> dashboard
```

## 1. Problem statement

IV bags run empty without anyone noticing, and gravity drip rates drift. A monitor should
estimate how long the infusion will last and warn before it ends. Single sensors each fail in
their own way, and the printed drop factor on the tubing is only approximate.

## 2. Motivation

- Nurses check bags periodically; an early, uncertainty-aware warning is more useful than a
  bare "empty" alarm.
- The drop factor printed on tubing (for example 15 drops/mL) differs from the real one, so a
  drop counter alone carries a systematic error.
- Disagreement between independent sensors is itself a reliability signal.

## 3. Why two sensors

| Sensor | Measures | Typical errors |
|---|---|---|
| Load cell (+ HX711) | bag weight, hence volume and flow | noise, drift, knocks, lost samples |
| IR drop counter | individual drops, hence drop rate | missed drops, phantom drops, timing jitter |

The drop sensor only reports `flow x drop_factor`, so it cannot separate the two. The load
cell reports flow directly. **Together, the drop factor becomes observable**, which gives
self-calibration.

## 4. Why an EKF

The drop-rate measurement `flow x drop_factor` is nonlinear in the state, so a linear Kalman
filter does not apply. The EKF linearises it with a Jacobian at each step. The
implementation (`src/ekf/ekf.py`) is written out explicitly in NumPy, with no filtering library.

## 5. Mathematical formulation

State and measurement:

```text
x = [flow (mL/min), drop_factor (drops/mL)]
z = [flow_from_weight (mL/min), drop_rate (drops/min)]
h(x) = [flow, flow * drop_factor]
H    = [[1, 0], [drop_factor, flow]]            (Jacobian at the current state)
```

Predict (random-walk model, F = I):

```text
x_k|k-1 = x_k-1          P_k|k-1 = P_k-1 + Q
```

Update:

```text
innovation y = z - h(x)         S = H P H^T + R         K = P H^T S^-1
x = x + K y                     P = (I-KH) P (I-KH)^T + K R K^T     (Joseph form)
```

Implementation notes: `K` is computed with `np.linalg.solve`, not an explicit inverse. If a
window has no valid weight, only the drop row of `h`, `H` and `R` is used. `Q` (flow wander)
and `R` (sensor noise) are in `config/config.yaml`.

Remaining volume and time:

```text
remaining_volume = (weight - empty_bag_weight) / density
remaining_time   = remaining_volume / flow_ekf
```

Confidence interval (first-order error propagation of `T = V/F`):

```text
sigma_T^2 = (sigma_V / F)^2 + (V * sigma_F / F^2)^2
interval  = T +/- 1.96 * sigma_T                (lower end clipped at 0)
sigma_F   = sqrt(sigma_EKF^2 + sigma_future^2) * (1 + g * relative_disagreement)
```

Assumptions: V and F errors are independent, errors are roughly Gaussian, and the
linearisation holds. `sigma_future` (flow may change before the bag empties) and
`g` (disagreement inflation) are **tunable heuristics, not measured quantities**.

Sensor disagreement: `|flow_weight - drop_rate / drop_factor_ekf| / flow_ekf`.

## 6. Simulation methodology

- **Truth** (`src/simulation/infusion.py`): piecewise flow (2.5 / 3.0 / 2.2 / 2.8 mL/min in
  5-minute segments, smoothed) plus a slow Ornstein-Uhlenbeck wiggle. Volume infused is the
  integral of flow; weight and cumulative drops follow from it, so both sensors are physically
  consistent by construction.
- **Load cell**: Gaussian noise, vibration, slowly drifting bias, decaying spikes, ADC
  quantisation and lost samples.
- **IR sensor**: drops placed where cumulative drops cross an integer, with timing jitter,
  missed drops (3%), phantom drops (0.5/min) and, in failure scenarios, double counting.
- **Initial EKF guess is deliberately wrong**: flow 2.0 mL/min, drop factor 15 (truth 14.5).
- One seed spawns independent random streams, so every run is reproducible.
- The EKF pipeline reads only measurement columns; `ref_*` columns (truth) are used for
  scoring and plots, and a test checks that predictions are identical without them.

## 9. Usage

```bash
python -m src.simulation.generate_data --plot   # 1. raw data -> data/raw/
python -m src.pipeline                          # 2. EKF + prediction -> data/processed/ekf_results.csv
streamlit run dashboard/app.py                  # 3. dashboard at http://localhost:8501
pytest -q                                       # tests
python -m src.experiments                       # experiments -> results/
```

Other commands: `python -m src.config` (show config), `python -m src.ekf.ekf` (EKF demo),
`python -m src.simulation.generate_data --scenario ir_missing_drops` (failure data; run
without `--scenario` afterwards to restore normal data).

Dashboard: choose *Live simulation* (sliders drive the real simulator and pipeline) or
*Saved results file* (replays `data/processed/ekf_results.csv`). Use Apply settings, then
Start / Pause / Reset / Jump to end / Generate New Dataset. Nothing on the dashboard is hardcoded.

## 10. Experiments

`python -m src.experiments` runs two experiments and writes CSV tables and interactive HTML
plots to `results/`.

**Sensor comparison** (mean of 5 seeds, first 10 windows excluded; flow in mL/min,
remaining-time error in minutes):

| Method | Flow MAE | Flow RMSE | Flow bias | Remaining-time MAE | Final drop-factor error |
|---|---|---|---|---|---|
| Load cell raw | 0.118 | 0.150 | -0.001 | 10.6 | n/a |
| Drop counter raw (printed DF) | 0.136 | 0.158 | -0.130 | 11.3 | n/a |
| EKF load cell only | 0.146 | 0.186 | 0.000 | 6.2 | +0.500 |
| EKF drop only | 0.163 | 0.195 | -0.130 | 9.0 | +0.500 |
| **EKF fusion** | **0.092** | **0.125** | -0.009 | 7.8 | **-0.198** |

**Sensor failures** (flow RMSE in mL/min inside the 60 to 100 min failure window):

| Scenario | Raw load cell | Raw drops | EKF load cell only | EKF fusion |
|---|---|---|---|---|
| Load cell 10x noisier | 1.418 | 0.139 | 0.498 | 0.274 |
| IR misses 20% of drops | 0.165 | 0.597 | 0.184 | 0.281 |
| Drop counter over-counts | 0.165 | 0.525 | 0.184 | 0.345 |

## 11. Results and interpretation

- **Fusion gives the best flow accuracy** (about 17 to 21% lower RMSE than either raw
  sensor) with near-zero bias, and is the only mode that learns the drop factor.
- **The learned drop factor settles near 14.3, not the true 14.5.** The IR sensor misses some
  drops and adds some phantom ones, so it effectively counts about 14.3 drops per mL. The EKF
  correctly calibrates to what the sensor actually reports.
- **Single-sensor EKFs have worse flow RMSE than the raw signals.** With one sensor and a small
  `Q`, the filter lags the 5-minute flow changes. The EKF pays off only with both sensors.
- **Fusion does not have the lowest remaining-time error**; the load-cell-only EKF does
  (6.2 vs 7.8 min). A plausible, untested explanation is that remaining time depends on the
  average *future* flow, which a smoother estimate approximates better. Remaining-time error is
  dominated by future flow changes, not sensor noise.
- **Fusion flags failures but does not reject the bad sensor.** With a fixed `R`, the fused
  flow lands between the two sensors. In the IR-missing and over-count scenarios, the load cell
  alone beats fusion inside the window. The disagreement alert fired within 1 to 2 minutes of
  onset in all three scenarios (in 70%, 18% and 15% of window samples respectively).
  Fusion strongly helps when the load cell becomes noisy.
- Part of a sustained discrepancy is absorbed into the learned drop factor over time, so the
  disagreement alert is strongest at the onset of a failure.

## 12. Limitations

- Everything is simulated. Real sensors have failure modes not modelled here (tubing
  kinks, air bubbles, bag swinging, patient movement, temperature effects).
- Preprocessing (spike filter and noise scale) looks a few seconds ahead, so the pipeline
  is an offline replay, not a strictly causal real-time filter. The EKF itself is causal.
- Adjacent windows share an edge weight sample, so their weight-flow errors are slightly
  correlated, which standard EKF theory assumes away.
- `R` and `Q` are fixed and were set from simulated noise levels. They are not adapted online.
- The Hampel spike filter occasionally flags a good sample (about 2 false alarms per
  600 samples in a test). The flagged samples are interpolated, so the effect on flow is small.
- The confidence interval uses a linearised, symmetric, Gaussian approximation. The
  `future_flow_std` and `disagreement_inflation` terms are heuristics, and the interval can be
  conservative. It is not a statistically calibrated guarantee.
- "Drop only" experiments still take remaining volume from the load-cell weight.
- Remaining time assumes the current flow persists; the true flow changes.

## 13. Future hardware integration

The simulator is isolated behind two CSV files (`timestamp, measured_weight_g` and drop
`timestamp`). Real hardware could replace it by logging the same columns, for example an
HX711 on a microcontroller and an IR break-beam sensor, with data sent by any transport.
The pipeline never reads `true_*`/`ref_*` columns. Real deployment would also need
calibration of the load cell, an online noise estimate (adaptive `R`), innovation gating to
reject a failed sensor, a causal real-time preprocessing filter, clinical validation and
regulatory work. None of this is implemented here.
